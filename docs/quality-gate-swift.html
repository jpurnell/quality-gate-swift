The problem

The worst bugs look correct.

Most quality problems in Swift aren't typos — they're structural. A force-unwrap that crashes on the one nil you didn't expect. An async stream whose cancellation path was never specified. A pointer that escapes the block that owned it. A division with no zero-guard.

These are invisible to a regex, and often invisible to a human reviewer — the code reads as fine. They are not invisible to a tool that parses the code the way the compiler does. quality-gate-swift walks the Swift abstract syntax tree via SwiftSyntax, so every rule understands scope, type context, and control flow. That precision is the whole point: false positives are rare enough that the tool can block a bad commit rather than add one more warning to a list nobody reads.

How it works

A gate, assembled from independent parts.

  • AST-first analysis. Each checker is a SwiftSyntax visitor that walks the parsed structure — it can tell value! from value != nil from a ! inside a string, and knows whether a guard already made the unwrap safe.
  • Modular by design. Every checker is its own Swift package target with its own tests and DocC docs. Depend on only what you need, or run the whole suite through one CLI.
  • Structured output, four ways. terminal for a developer, json for dashboards, sarif for GitHub Code Scanning (findings inline on your PR), and xcode for build-phase warnings in the IDE.
  • Auto-fix that's verified. Fixable rules repair with --fix (preview via --dry-run). Each fix is round-trip-tested: apply, re-parse, confirm the rule stays silent.
  • No override culture. Exemptions exist — but each is a single inline comment stating why (// SAFETY:, // Justification:), recorded rather than silent. You can see every place the rules were consciously relaxed.

Case study — Harbor

The bug that TDD didn't catch.

Harbor is a biofeedback headset product — a multi-package Swift workspace processing real-time data off the headset. Concurrent, async, sensor-driven, shipping to real users. It is exactly what this tool is built for — and it's where several of the tool's most valuable checkers were born, because a real bug got through everything else first.

◆ Incident

A session could end two ways: complete on its own, or the user could stop it — semantically different outcomes. The loop consumed sensor data with for try await over an AsyncThrowingStream. The author handled two exits: the stream finishes, or it throws.

But there's a third. When the task is cancelled, a for try await on an AsyncThrowingStream ends quietly — the iterator returns nil; it does not throw. So a user-initiated stop fell straight through to session.markCompleted() and was silently recorded as a completed session.

survived Design-First TDDsurvived 3+ green gate cyclesonly surfaced under scheduler stress

It was invisible to review — the code looked correct. Invisible to the suite — which passed, twice, on a byte-identical package. A scheduler-dependent race, not an error you could point at.

Three checkers came out of it

Rather than fix the one bug and move on, the failure became the specification for three new detectors:

  1. cancellation-checkpoint-after-loop — flags an await loop, in a function that already treats cancellation as meaningful, followed by exit-reason-dependent code with no post-loop cancellation check. Catches the exact Harbor shape before it ships. (AST-based: it has to know the function boundary and walk the loop's following statements in order.)
  2. test-outcome flip detector — persists a per-package pass/fail roster and flags any test whose outcome flips while the package fingerprint is unchanged. A flip on byte-identical source is a definitive race signal — and names both commits to bound the regression window.
  3. timing-tagged stress mode — re-runs // TIMING:-marked tests N times under CPU contention and flags any that aren't unanimous. It provokes the race deliberately, instead of waiting for the scheduler to expose it by accident.

✓ The precision lesson

Harbor also stress-tested the tool's false-positive discipline. An early unreachable-code run against Harbor emitted ~1,064 findings — almost all from a vendored SDK the team couldn't change. A gate that cries wolf 1,064 times is a gate people learn to ignore. Tightening the checker drove Harbor from 1,064 findings to 0; the same discipline later collapsed a 14,000-row duplication storm down to 11 genuine findings.

A quality gate is only as valuable as it is trusted, and it is only trusted if nearly every finding is real. Precision isn't a nicety — it's the product.

Compliance

Coverage, not a compliance badge.

SOC 2, ISO 27001, and HIPAA are mostly organizational frameworks — audited over time by people, not provable from source. A static analyzer sees only the technical slice. So quality-gate-swift refuses to print compliant. It reports coverage: which controls a rule actually enforces, which the gate's own operation evidences, and which are honestly out of reach — with the boundary stated in every report.

This is technical-control coverage — NOT an assertion of compliance. hipaa-security-rule [enforced] 164.312(e)(1) Transmission security ← security.insecure-transport, security.tls-disabled [out-of-scope] 164.312(b) Audit controls soc2-tsc [enforced] CC6.1 Logical access security ← keychain-secrets, security.weak-crypto … [evidence-only] CC8.1 Change management ← the gate itself [enforced] P1.1 Privacy notice ← privacy-manifest Summary: 12 enforced · 2 evidence-only · 2 out-of-scope · 0 gap

Behind that report is a mapping the gate keeps honest, and a monitor that keeps it current:

  • Two technical-control checkers. keychain-secrets catches credentials written to UserDefaults instead of the Keychain; privacy-manifest catches a missing or malformed PrivacyInfo.xcprivacy before the App Store bounces it.
  • A self-validating mapping. The control-mapping checker runs on every gate: a mapping pointing at a rule that doesn't exist, or a control no catalog defines, is an error — the same hallucinated-reference guarantee applied to the compliance layer itself.
  • The honest artifact. quality-gate compliance emits the coverage matrix across HIPAA §164.312, SOC 2, and ISO 27001 Annex A — as text or JSON — with out-of-scope controls named, not hidden. (Copyrighted standards are stored as our own paraphrase plus citation, never redistributed text.)
  • Drift that can't stay silent. standards-watch hashes the live HIPAA rule text from the federal eCFR API; when the regulation is amended, the hash changes and the check exits non-zero — a dated alert, not a surprise at audit time. It also reads the Federal Register for proposed changes to 45 CFR 164, so a rulemaking is on your radar before it even takes effect. It only detects and alerts; a human reconciles. Ships with a weekly launchd job to run it unattended.
The tool never claims you are compliant. It shows exactly what static analysis enforces, evidences, and cannot reach — and refuses to blur that line. That refusal is what makes it trustworthy instead of a liability.

In the workflow

It sits inside development, not beside it.

The tool enforces a strict TDD cycle — and because it runs the build and the full test suite too, "verified" means the whole thing is green, not just that the code compiles. The sequence matters, so it's numbered:

1 DESIGN→ 2 RED→ 3 GREEN→ 4 REFACTOR→ 5 DOCUMENT→ 6 VERIFY
  • Pre-commit hook — blocks a commit that introduces a violation. No skip flags; fix the root cause.
  • Pre-push hook — a fuller pass before code leaves the machine.
  • CI (GitHub Actions) — emits SARIF; findings appear inline on the pull request. One canonical run path shared with the local hooks, parity proven byte-for-byte.
  • Xcode build phase — findings surface as native warnings while you code.
  • Dashboard & telemetry — per-project gate status, honestly distinguishing green confirmed by a full run from green assembled from partial re-runs.
Write a failing test, make it pass with the minimum change, refactor, document, then drive the gate to zero errors and zero warnings — without overrides — and only then is the work done.

Getting started

Run it in a minute.

# build from source
git clone https://github.com/jpurnell/quality-gate-swift.git
cd quality-gate-swift
swift build -c release
cp .build/release/quality-gate /usr/local/bin/

# run everything
quality-gate --check all --continue-on-failure

# just the correctness-critical checks
quality-gate --check build --check safety --check concurrency

# preview / apply auto-fixes; SARIF for GitHub Code Scanning
quality-gate --fix --dry-run
quality-gate --format sarif > results.sarif

Configuration lives in .quality-gate.yml — which checkers, exemption keywords, per-rule severity overrides, exclude patterns. Requirements: macOS 14+, Swift 6.0+. License: MIT.
